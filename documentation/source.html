Overview

The On-call Runbook Copilot is an incident-response web app for the engineer on call. Alerts become incidents. For each one, the copilot finds the runbook that matches the symptoms, checks that runbook's claims against the service's own logs, and reports the root cause, the log lines that prove it, and the next steps, streaming every step to the browser as it happens. If no runbook is confirmed by the logs, it answers UNKNOWN and escalates instead of guessing. Engineers acknowledge, assign, take notes, edit runbooks and get a postmortem draft built from the incident record.

Stack: React + TypeScript (Vite) · FastAPI · PostgreSQL with SQLAlchemy 2 and Alembic · Server-Sent Events · JWT + bcrypt · Docker Compose · GitHub Actions · Render blueprint.

It runs against a real system: the platform API of HOI (Hospitality Operations Intelligence), a multi-tenant FastAPI + MongoDB service. HOI's code is not modified; faults are injected from outside by swapping dependencies HOI already isolates, so the copilot reads exactly the log lines HOI writes in production.

Deduplication that holds under concurrency

An alert whose fingerprint matches an open incident only increments a counter and adds a timeline entry, so nobody is paged twice. open_fingerprint equals the fingerprint while the incident is open and becomes NULL when it is resolved; its unique constraint means two identical alerts arriving at the same moment cannot both open an incident: the second insert fails and is folded into the first. A test fires 8 identical alerts in parallel and expects exactly one incident with count 8.

Workflow

triggered → acknowledged → investigating → resolved. A false alarm can be resolved straight from triggered or acknowledged; resolved is final, and resolving requires a resolution text. Invalid moves return 409 with the allowed ones. MTTA and MTTR are the mean and median minutes from creation to acknowledgement and to resolution.

Live investigations

The copilot's investigate() gained one optional argument, an observer called after each step (alert rules, query, retrieval, each runbook's checks). It only observes, so the diagnosis is unchanged. The web app runs it as a background task:

  1. The incident's log lines are loaded back into the copilot's own log store in order, so the ids it cites are the incident's line numbers.
  2. The readiness probe captured with the alert is replayed to the health tool (or the probe's failure, if the service was not running).
  3. Each step is committed to investigation_steps, with the cited log lines attached to each check.
  4. The browser reads GET /api/investigations/{id}/stream: Server-Sent Events, one step event per step (id = step number) and a final done.

The stream is read with fetch and a small parser rather than EventSource, so the session token goes in the Authorization header and never in a URL; after a dropped connection the client reconnects with Last-Event-ID and the server resumes after that step. Steps are paced (350 ms by default) so people can follow them; the copilot's own time is reported separately.

Equivalence test. For all 9 faults, the copilot is run on the live HOI instance and on the stored, replayed log window; the verdicts and cited log ids are identical.

Runbook library

Runbooks live in Postgres in the same markdown format as runbooks/*.md and are parsed by the copilot's own parser, so what saves is exactly what the investigator reads. Validation reports invalid JSON in the checks block (with its line number), unknown tools (the list comes from the read-only Tools class, so a "restart_service" check is impossible), arguments that do not fit the tool's signature, unknown operators, missing sections and an id change. Saving creates a new version; the editor sends the version it started from and gets 409 if someone saved in between. The retriever is rebuilt only when a runbook changes, and each investigation records which versions it used.

The problem

At 3 a.m. an alert says "38% of requests are failing". The engineer must work out why: is the database down, did a deploy break configuration, is someone attacking the login endpoint? Teams write runbooks ("if you see X, check A, B and C; the cause is usually D"), but under pressure people pick the wrong runbook, or trust a symptom that several different causes share.

The hard cases are look-alike incidents:

SymptomPossible causes that look the sameWhat separates them
High latencySlow database · cold start after idleIs the slowness sustained, or only in the first requests?
Spike of HTTP 401Signing secret rotated · password guessing · normal token expiryAre the 401s spread over many endpoints, concentrated on /auth/login, or a trickle?
Spike of HTTP 429Rate limit set too low · brute-force attackWhich endpoints get 429: guest chat across rooms, or the login endpoint?
AI answers degradeProvider rate limit · missing API key · model output changedThe exact fallback reason in the logs

A pure search or LLM approach picks by wording and confuses these. The copilot picks by evidence.

How an incident is investigated

1. Alert

Alert rules run over the log store. Each alert carries a summary and the ids of the log rows that triggered it. Thresholds are assumptions for a small service (tens of requests per window), for example 5xx share ≥ 10% or p95 latency ≥ 400 ms.

2. Query

The investigator writes the query an engineer would type: the alert names and summaries, the three most frequent warning/error templates (log lines with ids, tokens and numbers replaced, so identical messages group together), and the most common AI fallback reason.

3. Retrieve

The query is ranked against runbook sections by two methods, which are fused by rank:

  • BM25: exact words such as ServerSelectionTimeoutError or 429. The tokenizer also splits CamelCase error names into words.
  • LSA vectors: TF-IDF reduced to 48 dimensions with truncated SVD, which captures words that occur together ("slow", "latency", "p95").

4. Verify

For each of the top 5 runbooks, in rank order, the investigator runs the runbook's checks. A check names a tool, its arguments, a field, an operator and a value:

{"tool": "status_count", "args": {"status": "5xx"}, "field": "share", "op": ">=", "value": 0.1}

The first runbook whose checks all pass is the diagnosis. Look-alike runbooks contain checks that rule each other out (for example, "slow database" requires slow_only_at_start == false; "cold start" requires it to be true).

5. Ground and report

Before anything is shown, a grounding gate checks that the runbook exists and that every cited log id exists in the store. The note lists the alerts, the diagnosis and severity, the root cause, up to six cited log lines and the runbook's diagnosis and mitigation steps.

Retrieval in detail

BM25

For a query term t and a section d:

score(t, d) = idf(t) · f · (k1 + 1) / (f + k1 · (1 − b + b · |d| / avgdl))
idf(t)      = ln(1 + (N − df + 0.5) / (df + 0.5))

f is how often t occurs in d. k1 = 1.5 limits how much repeating a word helps; b = 0.75 corrects for long sections; the +1 inside the logarithm keeps very common words from getting a negative weight.

Reciprocal Rank Fusion

rrf(runbook) = 1 / (60 + rank_bm25) + 1 / (60 + rank_dense)

RRF uses only ranks, so the two score scales (BM25 sums and cosine similarities) never need to be calibrated against each other. A runbook's score is that of its best section.

Evaluation

55 scenarios: 11 types × 5 variants with different seeds, fault strengths and background noise (typo logins, 404s). Five modes form an ablation, to show what each part contributes.

ModeCorrect (all 55)Correct (41 detected)Wrong root cause
Hybrid retrieval + log-verified checks (the copilot)93%100%0
Hybrid retrieval, top-1, no verification87%93%3
BM25 only, top-187%93%3
LSA vectors only, top-187%93%3
BM25 + verification93%100%0
  • Verification removes the wrong answers (3 → 0): retrieval by wording confuses the look-alike pairs.
  • Dense retrieval adds nothing here: 16 short runbooks full of exact error names favour keywords. It should matter with paraphrased alerts or many more runbooks.
  • All 4 misses are detection misses, not wrong diagnoses: 8 and 12 password guesses stay under the login limit, and chat limits of 5 or 8 per minute were not hit by the test traffic.
  • No false alarms on 10 scenarios with nothing wrong, including the portal outage that HOI absorbs.
Honest caveat. The same person wrote the faults, the alert rules and the runbook checks, so these numbers are optimistic. They show the pipeline works end to end on a real codebase and how its parts compare; they are not an accuracy estimate for unseen production incidents.

LLM investigator (optional)

copilot/llm_agent.py lets an LLM choose the tools through function calling (any OpenAI-compatible API: Groq, OpenAI or a local Ollama). Its final answer must be JSON with a runbook id and cited log ids, and it passes the same grounding gate plus one more rule: cited log ids must have been returned by a tool during this investigation, so the model cannot invent evidence. It is implemented but not yet evaluated, so no accuracy is claimed for it.

Safety and design decisions

  • Read-only tools. The copilot never restarts, rolls back or changes anything; a human applies the fix.
  • Abstain rather than guess. A wrong root cause at 3 a.m. sends people down the wrong path; UNKNOWN escalates.
  • Evidence over wording. Retrieval only proposes; checks against the logs decide.
  • No secrets in logs. HOI never logs the database URI or guest messages; the copilot only reads what HOI writes.

Limitations

  • Faults are single and clean; real incidents overlap (a slow database that then times out).
  • About 60 requests per scenario from one process; thresholds are set for that scale.
  • LSA is learned from 16 runbooks; a pretrained embedding model would generalise better and can be plugged in through Embedder.
  • All HOI data is synthetic demo data.
  • One API process: simulations run one at a time (the harness changes process-wide state) and the SSE stream polls Postgres every 250 ms. Several instances would need LISTEN/NOTIFY or a queue and a separate worker.
  • Alerts carry their log window; a real deployment would pull logs from the log platform.
  • The 5 demo incidents are real simulations with made-up, backdated response times, labelled demo; the dashboard's MTTA/MTTR include them.

Interview questions

Why not just ask an LLM what is wrong?
It would answer from wording and could invent causes. Here every diagnosis must be confirmed by checks on the real logs and cite log lines that exist; otherwise the answer is UNKNOWN.
What does BM25's k1 do? And b?
k1 caps the benefit of repeating a word (term-frequency saturation); b scales how much long documents are penalised.
Why Reciprocal Rank Fusion instead of adding scores?
BM25 scores and cosine similarities are on different scales; RRF only uses ranks, so no calibration is needed.
How do you know it works?
55 injected faults on a real API, five-mode ablation, zero false alarms, and verification taking wrong diagnoses from 3 to 0. And I state that the numbers are optimistic because I wrote the faults and the checks.
How do you stop two identical alerts from opening two incidents?
A unique column that holds the fingerprint only while the incident is open. Two concurrent inserts cannot both succeed; the loser folds its alert into the winner. A "check, then insert" in Python would race.
Why fetch instead of EventSource for the live stream?
EventSource cannot send an Authorization header, and tokens in URLs end up in logs. fetch with a small parser keeps the header and still supports Last-Event-ID resume.
How do you know the web app gives the same verdict as the evaluated copilot?
It calls the same function on the same log lines, in the same order, with the same health result; a test compares live and replayed verdicts and cited ids for all 9 faults.
What would you do next?
Evaluate the LLM mode, add overlapping faults, use a pretrained embedding model, and test on runbooks and incidents written by someone else.
